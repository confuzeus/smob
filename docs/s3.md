# S3 and MinIO

smob writes each completed chunk as one object and queries by listing and
reading those objects. This guide covers the IAM policy, the AWS credential
chain, and a local MinIO setup. Chunk keys, immutability, and spool semantics
are described in the [README's storage section](../README.md#storage); the
disk-to-S3 copy, verification, and rollback procedure is in
[migration.md](migration.md).

This page covers only the fields needed to deploy against S3. The full
field-by-field configuration reference is in
[configuration.md](configuration.md).

## What smob does against S3

| Operation | When smob issues it | IAM action |
| --- | --- | --- |
| `HeadBucket` | At `collect` startup, including `--dry-run` and `--once`; retried on transient failures. | `s3:ListBucket` |
| `PutObject` with `If-None-Match: *` | For each completed chunk, and for spool replay; retried on transient failures. | `s3:PutObject` |
| `GetObject` | During `query` and `stats`, and to verify an ambiguous `PutObject`. | `s3:GetObject` |
| `ListObjectsV2` | During `query` and `stats`, to discover hosts and scopes and to list one UTC hour. | `s3:ListBucket` |

`query` and `stats` share one read path: both list the bucket, list the local
spool, and read every chunk in the requested range. `stats` needs exactly the
same `s3:ListBucket` and `s3:GetObject` permissions as `query`; nothing extra is
required for it.

Every object key is below `<prefix>/<host>/<scope>/` when `prefix` is set, or
below the bucket root when it is empty. smob does not create buckets, change
bucket settings, use multipart uploads, or write object tags or ACLs.

**smob never calls `DeleteObject`.** Deleting a spool file after a successful
replay is a local filesystem operation. S3 retention is a bucket lifecycle
rule, which S3 applies without the smob identity holding delete permission.
Grant `s3:DeleteObject` only if the same identity is also used by separate
tooling that deletes objects from the bucket.

## IAM policy

Attach this policy to the identity used by both `collect` and `query`. Replace
`smob-metrics` with the bucket name and `smob` with `storage.s3.prefix`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "HeadBucketAndListPrefix",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::smob-metrics",
      "Condition": {
        "StringLikeIfExists": {
          "s3:prefix": ["smob/*"]
        }
      }
    },
    {
      "Sid": "ReadWriteChunks",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::smob-metrics/smob/*"
    }
  ]
}
```

The `s3:ListBucket` grant looks broader than a prefix-scoped reader needs.
The statement does two jobs:

- `HeadBucket` requires `s3:ListBucket`, and the request carries no
  `s3:prefix`. A plain `StringLike` condition would be false for that request,
  so `collect` would exit 3 before collecting despite the rest of the policy
  being correct. `StringLikeIfExists` ignores the condition when the key is
  absent, which lets the bucket check through.
- `query` lists with a prefix such as `smob/` or
  `smob/web-1/system/2026/10/24/07/`. Those requests do carry `s3:prefix`, so
  they must match `smob/*`. The trailing `*` also matches the root prefix
  `smob/` itself.

This does not make bucket-wide listing impossible: the identity can still send
a deliberately prefixless `ListObjectsV2` and see object names in the bucket
(not object contents). The condition constrains smob's own listings, not an
adversarial caller. Use a dedicated bucket when key-name visibility outside
the prefix matters.

The policy assumes a non-empty `prefix`. With an empty prefix, smob lists the
bucket root by definition: use `arn:aws:s3:::smob-metrics/*` for the objects
and drop the `s3:prefix` condition, accepting bucket-wide object access and
listing within that bucket.

The object actions are scoped to the prefix. The bucket ARN is used only for
`s3:ListBucket` (`HeadBucket` and `ListObjectsV2`). There is no
`s3:DeleteObject` statement, no `s3:ListAllMyBuckets`, and no
bucket-administration permission. The separate credentials that run a
disk-to-S3 `aws s3 sync` are tooling credentials, not the runtime identity
described here; see [migration.md](migration.md) for the copy procedure and the
tooling permissions. That tooling identity needs only `s3:ListBucket` and
`s3:PutObject` for the copy: `aws s3 sync` compares size and modification time
from the listing and uploads missing objects, so it does not call `GetObject`
and needs no read permission on object bodies. It needs no `s3:DeleteObject`
either, because the documented copy is additive and never uses `--delete`.

## MinIO policy

MinIO accepts the same policy shape, but the MinIO release used by smob's test
suite does not implement the `...IfExists` condition operators. With
`RELEASE.2026-08-04T00-00-00Z`, `mc admin policy create` rejects
`StringLikeIfExists` with `invalid condition name`. Use this equivalent policy
on MinIO: the first two statements permit the prefixless `HeadBucket` and
limit listings to the chunk prefix; the third matches the AWS object grant.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "HeadBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::smob-metrics",
      "Condition": {
        "Null": {
          "s3:prefix": true
        }
      }
    },
    {
      "Sid": "ListPrefix",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::smob-metrics",
      "Condition": {
        "StringLike": {
          "s3:prefix": ["smob/*"]
        }
      }
    },
    {
      "Sid": "ReadWriteChunks",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::smob-metrics/smob/*"
    }
  ]
}
```

## Credentials

smob uses the standard AWS SDK credential chain. Credentials are resolved from,
in order:

1. Environment variables: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and
   `AWS_SESSION_TOKEN` for temporary credentials.
2. Shared configuration and credentials files, including `AWS_PROFILE`,
   `AWS_CONFIG_FILE`, and `AWS_SHARED_CREDENTIALS_FILE`.
3. Container and instance roles: an ECS task role, an EKS service account
   role, or an EC2 instance profile.

No credential field exists in `smob.yaml`; the `storage.s3` section contains
only the endpoint, region, bucket, prefix, and spool settings. `smob config`
prints the effective configuration verbatim, so do not embed credentials in
the `endpoint` URL.

When nothing is configured — no environment variables, no shared profile, no
container role — the chain probes the EC2 instance metadata service (IMDS). On
a host that is not an EC2 instance, that probe can add a few seconds to startup
before the chain gives up; the SDK's IMDS client bounds each operation at five
seconds and backs off before returning. Set
`AWS_EC2_METADATA_DISABLED=true` on a local MinIO host or any host where IMDS is
unreachable to skip the probe. Do not set it on an EC2 instance that relies on
its instance profile: it disables that credential source as well. Credentials
supplied by the environment or shared files are found without the probe, so the
delay only appears when the chain has to fall through to the metadata service.

Startup behavior differs by command:

- `collect` validates the store before collecting. It calls `HeadBucket` and
  probes the spool directory. Missing or invalid credentials, a missing
  bucket, or an unreachable endpoint fail startup with exit code **3** and a
  `persistent store failure` message. This applies to `--dry-run` and `--once`
  as well.
- `query` has no startup probe. It fails on its first list or get with exit
  code **1**. A host that can collect is therefore not proof that its query
  credentials work, and the reverse is also true.
- `smob config --validate` checks only YAML decoding and validation. It does
  not contact S3 and cannot detect bad credentials.

## Custom endpoints and MinIO

The `storage.s3` fields that matter for a non-AWS endpoint:

| Field | Behavior |
| --- | --- |
| `endpoint` | Absolute `http` or `https` URL. Empty means AWS S3. |
| `region` | Required when `endpoint` is empty. When only `endpoint` is set, smob defaults it to `us-east-1`. MinIO ignores the region, but the SDK requires one for request signing. |
| `path_style` | Unset defaults to `true` when `endpoint` is set and `false` for AWS S3. Path-style keeps the bucket in the URL path. Set it explicitly only when the service requires virtual-hosted style (`bucket.host`) and DNS supports that name. |
| `bucket` | Bucket name. The bucket must already exist; smob does not create it. |
| `prefix` | Key root inside the bucket. Leading and trailing slashes are trimmed. Empty means the bucket root. A non-empty prefix is recommended so the IAM policy can scope object access. |
| `spool_dir` | Local spool directory. Defaults to `<data_dir>/spool`; required when `data_dir` is empty. |
| `spool_max_bytes` | Spool cap in bytes. Defaults to 1 GiB when omitted. `0` does not disable the cap: validation rejects any value at or below zero with `storage.s3.spool_max_bytes: must be greater than zero`, even when `primary` is `disk`. |

### Plain HTTP is clear text

`endpoint` accepts `http://`, which is convenient for a MinIO instance on the
same host and unsuitable for anything else. Over plain HTTP the SigV4
`Authorization` header, the access key ID, every object key, and every chunk
body — metric names, label values, samples, and host names — travel in clear
text across the network, and nothing checks that the responses come from the
service you configured. Anyone who can observe the path can read the metrics,
and anyone who can intercept it can alter what `query` returns.

Keep an `http` endpoint on loopback (`127.0.0.1`, `[::1]`, or a Unix socket
forwarded locally) or on a private network you control, and use `https` with a
trusted CA for any endpoint reached over a shared or untrusted network. The
recipe below publishes MinIO on `127.0.0.1` only (`-p 127.0.0.1:9000:9000`) for
that reason.

A complete configuration for the local MinIO recipe:

```yaml
data_dir: ./data
host: web-1
sources:
  system:
    enabled: true
storage:
  primary: s3
  s3:
    endpoint: http://127.0.0.1:9000
    region: us-east-1
    bucket: smob-metrics
    prefix: smob
    path_style: true
    spool_dir: ./data/spool
    spool_max_bytes: 1073741824
```

With this file, `smob config` prints `region: us-east-1` and
`path_style: true`. Both are explicit here for clarity; omitting them produces
the same effective values because the endpoint is set.

Start MinIO with the image pinned by digest, as the integration suite does:

```sh
docker run -d --name smob-minio \
  -p 127.0.0.1:9000:9000 \
  -e MINIO_ROOT_USER=minioadmin \
  -e MINIO_ROOT_PASSWORD=minioadmin \
  --entrypoint /usr/bin/minio \
  pgsty/minio:RELEASE.2026-08-04T00-00-00Z@sha256:b6bfe7239bfc83fb90d31612d9704d86039dd714f7904b3f1ad68f211e602372 \
  server /tmp/minio --console-address :9001
```

The image includes `mc`, so the setup can run without installing a client on
the host. Export the root credentials and create the bucket:

```sh
export AWS_ACCESS_KEY_ID=minioadmin
export AWS_SECRET_ACCESS_KEY=minioadmin
export AWS_EC2_METADATA_DISABLED=true

docker exec smob-minio mc alias set local http://127.0.0.1:9000 \
  "$AWS_ACCESS_KEY_ID" "$AWS_SECRET_ACCESS_KEY"
docker exec smob-minio mc mb --ignore-existing local/smob-metrics
```

To run smob as a restricted writer/reader instead of the MinIO root user, save
the MinIO policy above as `smob-policy.json`, then create and attach it:

```sh
docker cp smob-policy.json smob-minio:/tmp/smob-policy.json
docker exec smob-minio mc admin policy create local smob-rw /tmp/smob-policy.json
docker exec smob-minio mc admin user add local smob-writer smob-writer-secret
docker exec smob-minio mc admin policy attach local smob-rw --user smob-writer

export AWS_ACCESS_KEY_ID=smob-writer
export AWS_SECRET_ACCESS_KEY=smob-writer-secret
```

Build smob, save the configuration above as `smob.yaml`, and run the documented
workflow:

```sh
just build

./smob config --config ./smob.yaml --validate
./smob collect --once --config ./smob.yaml
./smob query --config ./smob.yaml --since 1h
```

`collect --once` writes one partial chunk per enabled scope and exits,
exercising the same store check as the daemon. Run
`./smob collect --config ./smob.yaml` for continuous collection. Stop and
remove the container when finished:

```sh
docker rm -f smob-minio
```

For AWS S3, omit `endpoint` and `path_style`; `path_style` then defaults to
`false` and the SDK uses the regional endpoint. Supply a real `region` and rely
on the instance role for credentials.

## TLS and private CAs

Set `endpoint` to an `https` URL to speak TLS. A MinIO server with its own
certificate, or any S3-compatible gateway behind a TLS terminator, uses the same
fields as the plain-HTTP recipe; only the scheme changes, and `path_style` keeps
the default from the table above (`true` for a custom endpoint):

```yaml
data_dir: ./data
host: web-1
sources:
  system:
    enabled: true
storage:
  primary: s3
  s3:
    endpoint: https://minio.internal.example:9000
    bucket: smob-metrics
    prefix: smob
```

`region` is omitted and resolves to `us-east-1`, the default whenever only
`endpoint` is set. Supply the value the service expects when it validates the
signing region.

smob exposes no TLS settings of its own. `storage.s3` has no field for a CA
file, a client certificate, or verification, and there is no command-line
equivalent of `--insecure` or `skip_verify`: certificate verification cannot be
disabled. The scheme in `endpoint` is the only TLS control, and the store never
falls back from `https` to `http`. A certificate that does not validate fails
`collect`'s startup `HeadBucket` with exit code **3** and a
`persistent store failure` message carrying the x509 error; `query` and `stats`
fail on their first request with exit code **1**.

Trust comes from the process's root store, so a private CA must be trusted there
before smob runs:

- `SSL_CERT_FILE=/etc/smob/private-ca.pem` names one PEM bundle to trust.
  Because it replaces the default bundle path, include the public roots as well
  if the same environment also talks to other HTTPS services, or use the system
  store instead. `SSL_CERT_DIR` overrides the certificate directories that are
  scanned. Go loads the root pool once per process, so restart `collect` after a
  change and set these variables in the environment that starts smob.
- Installing the CA in the system store also works and suits a systemd service:
  drop the PEM under `/usr/local/share/ca-certificates/`, run
  `update-ca-certificates` (or the distribution's equivalent), then restart
  `collect`. For a single unit, an `Environment=SSL_CERT_FILE=…` line is the
  alternative to changing the system store.

`AWS_CA_BUNDLE` is not a supported path in smob. The SDK reads it and attaches
the PEM to the HTTP client it would build, but smob installs its own client on
the S3 service options to bound the transport timeouts
([client.go](../internal/store/s3/client.go)); that replaces the SDK client and
discards the bundle, so the connection is still verified only against the
default roots. A `ca_bundle` entry in the shared config is ignored for the same
reason.

Mutual TLS is not configurable: smob presents no client certificate. The
standard Go proxy variables (`HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY`) are
honoured by the transport and are the only network-path settings available.

## Operational notes

Each request attempt has a 30-second deadline and the HTTP transport bounds
dial, TLS handshake, response-header, and idle waits, so an endpoint that accepts
connections but never answers exhausts the retry budget and falls back to the
spool instead of blocking collection. The final flush on `SIGINT` or `SIGTERM`
is also bounded, at 30 seconds.

### Spool

A chunk that still cannot be uploaded after the retry budget is written to the
spool instead of being dropped. The spool file keeps the candidate key the
failed upload was trying: when the base key was already taken and the `-1`
attempt failed transiently, the entry is `…-1.jsonl.gz`, so replay uploads it at
that exact key instead of colliding with the occupied base object. When every
suffixed name through the collision cap is taken, the chunk is spooled under the
base key as a last resort and the condition is logged at `warn`; the bytes are
still preserved locally. A terminal rejection — `400`, `401`, `403`, or a
`404` that absence does not explain — is not spooled: `collect` fails with exit
code **3**, because a replay of revoked credentials or a denied permission could
never succeed and a growing spool would evict recoverable chunks. `spool_dir`
defaults to `<data_dir>/spool`. Startup creates the directory if needed, probes
it with a temporary file, and fails with exit code **3** when it is not
writable. If `data_dir` is empty, `spool_dir` must be set explicitly.

`spool_max_bytes` caps the total size of spooled chunks. The default is 1 GiB.
The value must be greater than zero: `0` is rejected at validation, not treated
as unlimited. When the cap is exceeded, the lexicographically oldest unprotected
chunks are deleted and every drop is logged at `error`; collection does not
block. A single chunk larger than the cap can leave the spool above the limit.

The spool is local, unencrypted gzip. Each entry is the same JSONL-gzip chunk
body that would have been uploaded, so process names and PIDs, container names
and images, and host interface names are readable to anyone who can read
`spool_dir`. smob performs no client-side encryption and sends no encryption
headers, so at-rest protection in the bucket is whatever the bucket's default
encryption policy provides; bucket IAM is the access control for the objects.
Treat `spool_dir` like `data_dir`: writable only by the collector's user, with
group read as the sharing mechanism and never group-writable
([configuration.md#trust-boundary](configuration.md#trust-boundary)).

Replay is started by `collect` only, in key order, and is stopped and waited
for on `SIGINT` or `SIGTERM`. A chunk written by the final flush after a failed
upload stays in the spool and is uploaded on the next `collect` start. Before
uploading, replay gzip-decodes the file and checks it against the chunk
encoding; a truncated or bit-rotted file is logged at `error`, left on disk for
an operator, and not retried again in that process, so corrupt bytes are never
published. Transient replay failures keep the file and back off from 30s up to
5m with equal jitter, so hosts that shared an outage do not retry in lockstep.
Replay treats identical existing bytes as success and deletes the spool copy; an
existing object with different bytes is a permanent conflict, logged at
`error` and left for an operator. Replay never creates a `-1` duplicate for an
upload that succeeded before its spool delete failed. `collect` applies
`spool_max_bytes` synchronously at startup, before any source can write, so a
pre-existing over-cap spool is trimmed before new chunks are staged; replay
itself never runs that initial trim.

`query` merges a readable spool with the bucket on the host running the query,
so locally spooled chunks remain visible before upload. `stats` scans through
the same path and merges the spool identically. A key present in both is read
from the bucket only, so a failed spool delete cannot duplicate samples. A
querying host without the collector's spool directory sees only the bucket; an
unreadable spool is an error, not silently ignored.

### Reading and writing

`storage.primary: s3` selects S3 for both `collect` and `query`; there is no
mirroring or dual-write. A query reads S3, not a local disk copy. To migrate
existing disk data, copy it first and then change `storage.primary`; see
[migration.md](migration.md).

Do not run two collectors with the same `host` and `prefix`. Multiple hosts may
share a bucket because every key starts with the host component and every
sample carries a `host` label.

To check a policy without waiting for a collection interval, run
`collect --dry-run` (bucket check and spool probe), `collect --once` (at least
one `PutObject`), and `query` or `stats` (listing and `GetObject`). No smob
command and no documented `aws s3 sync` copy requires `s3:DeleteObject`.
