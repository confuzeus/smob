# smob v0.3 — Scoping Draft

> **Status: draft, not a roadmap.** No v0.3 work is scheduled, prioritized, or
> dated. This document records the candidates deferred from v0.2, the questions
> each must answer, and the evidence that would justify building it. Nothing
> here is a commitment, and nothing here describes behavior that exists today.
> The order of the sections carries no meaning.
>
> `v0.2.0` is tagged locally but has not been published, so there are no users
> and no feedback to evaluate yet. This draft exists so that the first real
> feedback has somewhere to land; it is not a substitute for that feedback.
> Current behavior is documented in the [README](../README.md) and in the
> [design and implementation plan](IMPLEMENTATION.md).

## Where these candidates come from

The three candidates are the ones already deferred in the design plan's
[Deferred to v0.3](IMPLEMENTATION.md#5-deferred-to-v03) section and restated in
its [non-goals](IMPLEMENTATION.md#6-non-goals-v02). The rationale for deferring
them — the chunk clock and storage layout, the absence of a server, the `host`
label — lives there and is not repeated here. This document adds only the open
questions and the evidence gate for each.

The v0.2.0 release notes describe these as "planned for v0.3". That is intent to
revisit them, not an order, a date, or a promise.

## 1. Live tail

**Today.** `smob tail` is a stub that exits with an error. Historical data is
read from completed chunks by `query` and `stats`.

**Why store polling cannot be a tail.** A chunk is closed and written once its
five-minute window ends (or on shutdown, or by `collect --once`); see
[Storage Format and Chunking](IMPLEMENTATION.md#3-storage-format-and-chunking).
A process that polls the store therefore sees a sample no earlier than the end
of its window — up to `storage.chunk_interval`, five minutes by default. That is
a delayed historical query, not a tail. Shortening the chunk interval does not
fix it: it trades latency for many more objects and more write and query work,
without removing the window boundary the delay comes from.

**Candidate transports.** The design plan already names two, without choosing
between them: a live spool that the collector appends to and `tail` reads, or a
local IPC endpoint exposed by the collector. Neither is designed.

**What must be decided before building it.**

- The transport and its framing: file append and follow, a Unix socket, or
  something else. Where the collector publishes, and how a client discovers it.
- The output contract: whether `tail` reuses the `query` output formats and
  label filters, and whether it replays the current partial window before
  switching to live samples.
- Safety: a Unix socket needs filesystem permissions and possibly peer
  credentials; a spool file needs its own permissions and a cleanup rule. Who
  may read live data from a host?
- Multi-client behavior: independent readers, a broadcast fan-out, or a bounded
  buffer per client. What happens to a slow client — drop oldest, disconnect, or
  block? Blocking the collector is not acceptable.
- Lifecycle: what `tail` does when no collector is running, when the collector
  restarts, and at chunk boundaries. Live tail is best effort and is not a
  durable replay mechanism.
- Backpressure and memory bounds for both the collector and the client.

**Evidence that would justify building it.** Recorded requests to watch a host
in real time while diagnosing a problem; operators currently polling
`query --since 1m` at a high frequency to approximate it; a described
operational task that historical queries cannot serve. "Other tools have a tail"
is not, by itself, evidence of demand here.

## 2. Chunk index

**Today.** A chunk has no sidecar index. Queries prune by host, scope, and UTC
hour, then list, open, decompress, and scan the chunks that overlap the range; a
chunk that contains no matching metric or label is still read. The design plan
records this in
[Storage Format and Chunking](IMPLEMENTATION.md#3-storage-format-and-chunking).

**What the sidecar would hold.** As sketched in the design plan: the minimum and
maximum timestamp in the chunk, the set of metrics it contains, and sample
counts. The sketch does not include a label index, and this draft does not add
one.

**When it is justified.** Only when measured query latency says the scan is the
bottleneck. An index costs an extra object or file per chunk, an extra write on
the collection path, a rebuild path for chunks written before the index existed,
and new failure modes when the index and the chunk disagree. That is not worth
paying for a hypothesis.

**How to measure before building it.** Use existing commands against a
representative real corpus, not synthetic data:

- a multi-week, multi-scope range on one host, and the same range with several
  hosts in a shared bucket;
- narrow queries (`--metric`, specific label matchers) that should touch a small
  fraction of chunks, and broad ones that legitimately scan everything;
- record wall-clock time and the number and total size of chunks in the range
  (derivable from the key layout) and, for S3, request counts and bytes
  transferred from the provider's metrics or access logs.

A target such as "narrow queries should not read every chunk in the range" is a
decision for the maintainer once numbers exist. Until those numbers are recorded
here or in an issue, the index stays deferred.

**Why adding it later is safe.** The index is sidecar data. The chunk format,
key layout, and sample schema do not change, so old chunks remain readable and a
missing index can fall back to a scan. There is no migration and no flag day.

**Open questions.** Index key and format; whether it is written in the same
atomic step as the chunk or can be rebuilt from it; how a stale or missing index
is detected; and whether the extra `PUT`/`LIST` traffic on S3 costs more than the
`GET`s it saves.

Compaction of small chunks is listed beside the index in the design plan. It is
a separate change and is not scoped here.

## 3. Multi-host aggregation and query

**What v0.2 already provides.** Every sample carries a `host` label and the
storage key path is `<root>/<host>/<scope>/...`, so several machines can write to
one bucket under the same prefix without colliding, as long as their host labels
are distinct. A single query can already
span hosts: omitting `--host` scans every host present in the store, `stats`
folds all matching hosts into one row per metric, and `--agg` groups across hosts
unless `host` is listed in `--group-by`. Per-host queries use `--host`. The CLI
contract is in the [README](../README.md#query).

**What is missing.** The design plan's shorthand is "no cross-host series
aggregation and no server". Precisely:

- No per-timestamp combination across hosts. Existing aggregation is over the
  scanned range (with rates weighted by `interval_ms`), not "cluster CPU at each
  instant" with timestamp alignment across hosts.
- No partial-failure semantics for a multi-host read: a host whose chunks are
  unreadable fails the query rather than contributing a clearly marked partial
  result.
- No remote query API. Querying requires read access to the same disk or bucket
  and its credentials; there is no endpoint that fans out to hosts, brokers
  results, or authenticates a client.

**Open questions.**

- Remote query: is the server the collector, a separate read-only process, or
  just documented access to shared object storage? What is the response format,
  and does it stream?
- Authentication and authorization: who may query a host, with what credential,
  and over TLS or a local socket. This is the largest unresolved question; a
  network query endpoint is a new security surface.
- Fan-out: pull from each host, read one shared bucket, or both. What bounds
  concurrency and response size?
- Partial failure: does one unreachable host fail the query, or return partial
  data with explicit warnings? Silent partial success is not acceptable.
- Clock skew and gaps between hosts, and whether aggregation is per timestamp or
  per range.
- Whether any of this belongs in the collector at all, given the one-writer per
  host and prefix model in
  [Guiding Principles](IMPLEMENTATION.md#1-guiding-principles).

**Evidence that would justify it.** Real deployments with multiple hosts in one
bucket; requests for a single cross-host view that `query` and `stats` cannot
produce; users who have data but not bucket credentials on the machine where
they want to query; and a concrete operational question that per-host queries
answer too slowly. A single-host deployment provides none of this.

## Not in scope, and undecided

- No dates, milestones, ordering, or priority. Nothing in this document is
  scheduled.
- This draft does not cover v0.4 or any feature beyond the three above.
  Alerting, dashboards, Prometheus exposition, distributed collection, sharding,
  downsampling, and multi-writer collection remain non-goals unless a future
  document says otherwise; see
  [Non-Goals](IMPLEMENTATION.md#6-non-goals-v02).
- No chunk format, key layout, or sample schema change is proposed. Anything that
  would break existing chunks needs its own decision.
- No transport, protocol, index format, API, or authentication scheme has been
  chosen. The questions above are open.
- No claim that v0.2.0 has been published. It is tagged locally; binaries and the
  image have not been pushed anywhere.

## What would move an item forward

1. Publish v0.2.0 and provide a feedback channel (issue tracker or equivalent).
2. Record observed usage and concrete requests, tying each to one of the three
   candidates.
3. For the index, record measurements from a representative corpus.
4. Update this draft and the design plan's TODO with that evidence, then decide
   whether to schedule the work.

Until then, this document stays a draft, and no v0.3 implementation work starts
from it.
